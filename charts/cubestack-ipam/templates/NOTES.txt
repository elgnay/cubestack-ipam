NEXT: CREATE A POOL
  kubectl apply -f https://raw.githubusercontent.com/suanova/cubestack-ipam/main/config/samples/ipam_v1alpha1_ippool.yaml

  Note the plural collision: Whereabouts already owns `ippools` in kube-system, so
  always use the full resource name.

    kubectl get ippools.ipam.cubestack.io

  Then check the pool was accepted -- some invariants (band ordering, gateway
  position) are enforced by the controller, not the API server, and a pool that
  fails them is still admitted:

    kubectl get ippools.ipam.cubestack.io -o jsonpath='{.items[*].status.conditions}'

THEN: TAG A VM
  Add ipam.cubestack.io/pool: <pool-name> to the VirtualMachine and point its
  networks[].multus.networkName at the NAD name you want minted
  (default <vm-name>-static). See config/samples/kubevirt_v1_virtualmachine.yaml.

  The VM will show FailedCreatePodSandBox for the few seconds between being created
  and its NAD being minted. That is expected and self-healing.

ALSO: RESERVE A BLOCK
  IPRangeRequest claims N contiguous addresses from an existing pool in one object,
  for a consumer that needs a range rather than a single address:

    kubectl get iprangerequests.ipam.cubestack.io -A     # short name: iprr
    kubectl get iprr -n <namespace> <name> -o jsonpath='{.status.start}-{.status.end}'

  Two things to know before using one. It is a reservation, not a deployment: nothing
  here configures whatever consumes those addresses, so deleting the object frees them
  for the next VM while that consumer keeps using them -- and on a `static` pool
  nothing refuses the duplicate. And this chart deliberately ships no write role for
  it, only a viewer, because that grant is worth making per team against a named pool.
  Read the README's deletion section first.

WHAT THIS DOES NOT DO
  It does not configure the guest, and it does not migrate existing VMs onto claims.
  The shared underlay NAD is not touched by this chart -- retiring it is a migration,
  not a deploy. See the README.

UNDERLAY INJECTION
{{- if include "cubestack-ipam.mapAPIVersion" . }}
  Installed. Every VirtualMachine created or updated in
  {{ join ", " .Values.map.namespaces }} carrying the ipam.cubestack.io/pool annotation
  gets its networks[].multus.networkName rewritten to <its own namespace>/<its own
  name>-static at admission, so pool members no longer share one reference.

    kubectl get mutatingadmissionpolicy {{ include "cubestack-ipam.fullname" . }}-vm-underlay
    kubectl get mutatingadmissionpolicybinding {{ include "cubestack-ipam.fullname" . }}-vm-underlay

  It fails closed: a VM in one of those namespaces that the expressions cannot
  evaluate is REJECTED, not admitted unmodified. Widen `map.namespaces` only as far
  as the namespaces that use pool claims.
{{- else }}
  NOT INSTALLED -- this cluster does not serve MutatingAdmissionPolicy.

  On 1.32-1.35 that is just the feature gate, which is off by default; 1.36 turns it
  on and serves the same object as v1. Nothing is broken: the controllers run, claims
  are minted, and VMs that name their own NAD keep working. What is missing is only
  the per-member rewrite, so a VirtualMachinePool member still takes the literal
  networkName from spec.virtualMachineTemplate -- one reference shared by every
  member, and on a `static` pool nothing refuses the duplicate.

  To turn it on, the API server needs BOTH flags. The gate alone is not enough: it
  starts the admission plugin, whose informers are hard-wired to the v1beta1 group
  version that 1.35 does not serve, and the plugin then refuses every request in the
  cluster -- including the API server's own.

    --feature-gates=MutatingAdmissionPolicy=true
    --runtime-config=admissionregistration.k8s.io/v1beta1=true

  Then re-run this install. Or set map.enabled=false to stop being told about it.
{{- end }}

METRICS
  HTTPS on port {{ .Values.metrics.port }}, requiring a bearer token that passes a
  SubjectAccessReview. To scrape it, bind your scraper's ServiceAccount:

    kubectl create clusterrolebinding <name> \\
      --clusterrole={{ include "cubestack-ipam.fullname" . }}-metrics-reader \\
      --serviceaccount=<ns>:<sa>

  A plain `curl` of /metrics returns 401 by design. To read it by hand:

    kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "cubestack-ipam.fullname" . }}-metrics {{ .Values.metrics.port }}:{{ .Values.metrics.port }}
    curl -k -H "Authorization: Bearer $(kubectl create token <sa> -n <ns>)" \\
      https://localhost:{{ .Values.metrics.port }}/metrics
